## What Ben asked for

- Answers that sound like a friendly conversation with me, not a serious lecture.
- Answers that tie back to class ("we covered this on these days") and then go beyond class when that helps, from verified sources.
- A way for students to say an answer helped or didn't (a thumbs up).
- A plan for getting feedback from students.
- Help with assignments.
- What v2 looks like, given that v1 was built in two days.

## Why v1 sounds like a lecture

v1 does what the spec asked: be safe, stay on the slides, decline the rest. It does that well. The lecture tone comes from six choices, and most are about structure rather than wording, so editing the prompt alone won't fix it.

1. **The shape is a monologue.** Every covered answer is 4 or 5 slides, with 60 to 90 spoken words per slide ([`narration.py`](../app/narration.py) `TARGET_WORDS`, `select_segments` cut to 5). That's 300 to 450 words, about two and a half minutes of me talking before the student can react. That's a mini-lecture by construction.
2. **Each segment narrates a slide.** The prompt asks for "exactly one segment per slide" and "refer to what is on screen". So the model describes slides. It never answers the student first and then shows the slides as evidence.
3. **The prompt rewards caution.** "Use ONLY the material", "do not add facts, examples ... or opinions", "if the material is thin, say less", "no hype" ([`prompts.py`](../app/prompts.py) `NARRATION_SYSTEM`). The safe way to follow that is to sound formal and flat.
4. **The code check penalizes warmth and examples.** The grounding check rejects a segment when more than half its content words aren't in the slides ([`narration.py`](../app/narration.py) `GROUNDING_MAX_UNGROUNDED_SHARE`). A fresh example or an upbeat aside is exactly what fails it. After one retry the segment falls back to my speaker notes or a transcript excerpt, which is the most lecture-like text there is.
5. **There's no conversation.** No acknowledgment of the question, no "we did this in class on September 22" (each slide's session and date are already in the payload), no invitation to keep going, and no memory of the previous question.
6. **Class and outside material can't mix.** `/api/ask` routes are first-wins. A question gets slides *or* a web answer, never both ([`main.py`](../app/main.py) `answer()`). The web answer is told to "write as a helpful guide, not as Ben", is shown as a separate text card, and is never spoken. So "Oh yes, we talked about agents in class, now here are some frameworks" is impossible today.

The evals add a seventh, quieter reason: the judges score grounding and scope most heavily. `engaging_voice` exists, but nothing is tuned against it, and there's no signal from students at all.

About 100 words and 40 seconds. "Go deeper" plays today's full walkthrough, so nothing from v1 is lost.

**Next to class, not in it.** "What kind of Python frameworks are out there for AI agents?"

>
> **Spoken, over a "Beyond class" card:** "The ones worth knowing are LangGraph, CrewAI, the OpenAI Agents SDK, and the Claude Agent SDK. LangGraph is the most flexible. CrewAI is the quickest way to get a team of agents talking. If you're just starting, I'd build the same loop from class in one of them and compare."
>

## Design principles

1. **Answer first, then offer more.** Lead with a 1 to 3 sentence answer. Show 1 to 3 slides by default. Make the full walkthrough one tap away.
2. **Talk to the student, not at them.** Acknowledge the question, connect it to class, explain, and invite them to keep going. Upbeat, but honest: "great question" only when it is, and varied.
3. **Class first, never class only.** Always anchor in what we covered and when. Go beyond class when it helps, from verified sources, and say out loud where class ends.
4. **Label the line.** "From class" and "Beyond class" are separate on screen and in the voice. A student should always know which is which.
5. **Safety stays in code.** PG, access codes, names, injection, signed audio, rate limits, and caps don't change. The grounding check changes from "the words must be in the slides" to "each claim must come from the slides or from a cited, allowlisted source".
6. **Every answer can be rated, and every rating feeds a loop.**

## The new answer shape

### One composer call instead of narration plus a web card

One model call returns a short plan:

```json
{
  "mode": "class" | "blend" | "outside",
  "opener": "<= 30 words: acknowledge, and name the class session and date when there is one>",
  "parts": [
    {"type": "class",  "slide_id": "<id>", "say": "<= 60 words"},
    {"type": "beyond", "source_ids": ["s1", "s2"], "say": "<= 70 words"}
  ],
  "invite": "<= 15 words",
  "follow_ups": ["...", "..."]
}
```

- The opener is spoken over the first part, as one segment. It's the simplest fit for the player: segments still map one-to-one to things on screen, so `onClipEnded` in `public/app.js` needs no change. Since Oct 8 the player is ordinary code, so a separate opener segment is also possible if it plays better.
- A "beyond" part is a segment with a card instead of a slide image: a title, the source links, and an optional AI-drawn helper slide (that feature already exists).
- The spoken default is about 150 words, around one minute. **Go deeper** asks for today's full walkthrough of the slides `select_segments` picked.

### Routing: from first-wins to coverage levels

The routes for alerts, stored topics, FAQ, personal requests, Canvas, and logistics stay as they are. The slide and web routes merge into one decision based on how well class covers the question:

| Coverage | Today | v2 mode |
| --- | --- | --- |
| A slide at or above the threshold (0.52) | Slides only | **class**, plus a "beyond" part when the question asks for more than class covered ("what frameworks", "what else", "in practice") |
| Best slide between the related floor (0.42) and the threshold | Web card with "closest material" | **blend**: anchor in the related session, then go beyond class |
| Below 0.42, and the question is course-adjacent | Web card | **outside**: "We didn't cover this in class, but here's what I'd look at", with no slide |
| Off-topic | Decline | Decline, unchanged, but friendlier copy |

A small classifier call decides "asks for more than class". It can share a call with the existing logistics check, so it adds no extra round trip. `rank`, `select_segments`, and the threshold can stay as they are: v2 only reads their output. Since Oct 8 they're ordinary code, so v2 can also change them, for example letting `select_segments` return 1 to 3 slides for the short answer.

### Verified sources

"Verified" needs to mean something the code can check, not something the prompt asks for.

- **Tier A, mine:** slides, class transcripts, Canvas, my readings list, my papers. Allowed everywhere.
- **Tier B, allowlist:** official documentation (Python, PyPI, scikit-learn, pandas, PyTorch, Hugging Face, LangChain/LangGraph, CrewAI), provider docs (Anthropic, OpenAI, Google), arXiv, and university pages. A default list ships with v2, and I can edit it in Settings.
- **Tier M, an approved model's own knowledge (added Oct 8, Ben's decision):** a beyond part can come from what a top-tier model knows, not only from a search, when the model writing it is on the approved list in Settings (to start: Claude Opus 5.5 and Astra). This is meant for stable ideas, such as what an agent framework is for or how two methods differ. Anything that changes over time (versions, prices, release dates, setup steps) still needs a Tier A or Tier B source.
- **Tier C, the rest of the web:** never spoken and never quoted. At most it's listed as "further reading", or left out.

How the code holds that line:
- The search call passes the allowlist to the provider's own domain filter. Anthropic's web search tool takes `allowed_domains`. Check OpenAI's and OpenRouter's equivalents before building.
- Links come only from the search tool's citation metadata, as today, and each one must be on the allowlist.
- Every "beyond" part either cites at least one source id or is marked `"source": "model"`.
- A cited beyond part's grounding check compares its words with the text of the cited search results, the same way class parts are checked against slides.
- A model-knowledge part has nothing to compare against, so it's only accepted when the model that wrote it is on the approved list. If the active model isn't on the list, the part is dropped and the answer keeps its cited parts, or falls back to today's web card. Every other check still applies: PG, names, access codes, no web addresses, the injection echo check, and the length caps. The card says "Beyond class: from Claude Opus 5.5" (or whichever model wrote it), so it's clear where it came from.
- The opener and invite are exempt from grounding, because they make no claims. In exchange they get a hard word cap, no numbers, no names, PG, and the echo check.

Today my cloned voice only ever says things grounded in my own slides. v2 has it say things from outside class too. The options were:

1. **My clone says everything, with a spoken handoff** ("this next part comes from outside class") and the Beyond class card. *Recommended.* It matches how I'd actually answer, and the allowlist plus per-part grounding keeps it to vetted facts.
2. **My clone for class, a stock voice for beyond class.** The boundary is audible, but switching voices mid-answer is jarring.
3. **Beyond class is text only, as today.** Safest, but it doesn't give the conversation Ben asked for.

### Sounding like me: the voice card

A prompt can't guess how I talk. Give it examples:

- **A voice card**, about 15 lines in Settings: how I open ("Hey, great question"), how I connect to class ("We did this on..."), words I use, words I never use, how much energy, how I end ("Want to go deeper?").
- **6 to 10 real examples** of me answering a question: from class transcripts where I answer a student (only my answer, since student speech is already stripped), and from my email replies, rewritten so no student can be identified. These are few-shot examples in the composer prompt.
- **Variety check in code:** the opener can't repeat the last few openers word for word, so it isn't "Great question!" every time.

## Student feedback

### In the answer: thumbs up and thumbs down

- **UI.** 👍 / 👎 under every answer, shown once the first segment has started. A thumbs down opens one-tap reasons:
  - Too long
  - Too formal
  - Didn't answer my question
  - Something's wrong
  - Show me more from outside class
  - Plus an optional comment of 200 characters or fewer
- **Data.** `/api/ask` returns an `answer_id` (stored on the `question_log` row). `POST /api/feedback {answer_id, rating, reasons, comment}` writes to a new `answer_feedback` table: `answer_id`, `at`, `rating`, `reasons`, `comment`. That's one rating per visitor per answer (rate-limited by the visitor key), with no names, accounts, or IP addresses, the same rule as the question log. Comments go through the same privacy and PG scrubbing as questions.
- **Implicit signals** to add to `usage.EVENT_NAMES`:
  - `go_deeper_tapped`
  - `answer_skipped` (the student asked something new before the first segment ended)
  - `rephrased` (a new question within 60 seconds that's similar to the last one, a strong sign the answer missed)

### Closing the loop in Settings > Feedback

An inbox of thumbs-down answers, newest first, showing the question, the answer, the reasons, and the mode. For each one I can:

- **Write my answer.** It's saved as a *golden answer*. It replays the next time the same question comes in (like the FAQ), becomes the eval reference for that question, and can be promoted to a voice-card example.
- **Add to evals.** The question joins the eval set, with my answer as the reference.
- **Note for class.** A to-do: "revisit X in class", or "this slide is confusing".

### Ask Ben

When a student gives a thumbs down, or the twin declines, offer **"Send this to Prof. Collier"**. It goes into the same inbox, anonymously. My reply becomes a golden answer that everyone gets. This is how the twin gets better every week without me retraining anything.

### Weekly digest

Every Monday, an email or text (the alerts code already sends texts):

- the share of answers marked helpful
- the 3 topics students asked about most, grouped by top slide and session
- the 3 most-disliked answers
- new Ask Ben questions

This is the twin working as a sensor for my teaching. "Five students asked about embeddings this week" is something I can act on Tuesday in class.

### Beyond the app

- **Five-student think-aloud** (15 minutes each, before and after Stage 2). The quickest way to hear "this sounds like a lecture" in students' own words.
- **Two-question pulse in week 6 and at the end of the semester** (Canvas survey): "What did you use the twin for?" and "What would make it more useful?"
- One question on the course evaluation.
- If I want to publish from this later, the feedback table plus the eval history is the dataset. That needs IRB review before collecting with research in mind, so decide early.

## Assignment help

Today, assignment questions go to Canvas course info (descriptions and due dates) or get treated as course content. The twin doesn't know what help is allowed on which assignment.

### Assignment coach

- **A help level per assignment, set in Settings.** Assignment titles and descriptions already come in from Canvas. Levels:
  1. Explain concepts only
  2. Hints and approach (*recommended default*)
  3. Review my work (explain errors and point to a fix)
  4. Anything my AI-use policy allows

  The page shows the level as a line: "For Assignment 3, I'm happy to give hints and review your approach, but not write it for you."
- **Coach notes from me, per assignment:** common pitfalls, what good work looks like, and which sessions set it up. They're private, like the FAQ's TA emails.
- **A hint ladder** in the answer: a conceptual nudge, then the slide and code from class, then a worked example on *different* data, then "bring it to office hours" (with Calendly). Each tap goes one rung further.
- **Guarded in code, not just the prompt:** a private list of solution fingerprints per assignment (key values, exact phrasings, function names from my solution). A reply that contains one is blocked, the same idea as `indexer/leakcheck.py` and the quiz filter. At "review my work", students can paste code or an error message. That's covered by the same privacy scrubbing, and it's never stored.
- **Before a deadline:** if one assignment's questions spike, send me an alert ("12 questions on Assignment 3 since yesterday, mostly about the merge step"). This reuses the instructor alerts code.

## Other ways to make answers more useful (ranked)

1. **Conversation memory within a visit.** Send the last 2 or 3 questions and answers as context, so "can you show that in code?" works. It's cheap, and it fixes many follow-up misses.
2. **Missed-class recap.** "I missed Tuesday, what did we cover?" gets a two-minute summary of that session in my voice, built from its slides and transcript, plus links to the recording and the slides. Missed class was a frequent category in the first eval, and the twin currently fails it.
3. **Quiz me.** Before an exam, the twin asks practice questions from a session's slides and gives feedback. The quiz and exam filters still apply, so no real assessment item can leak.
4. **Show the code running.** Code slides get an "Open in Colab" link to the class notebook.
5. **Listen or read.** A toggle and a 1.25x speed button. Some students want to skim.

## Evals for v2

- **New judge dimensions:**
  - `sounds_like_ben` (warm, upbeat, conversational)
  - `connects_to_class` (names the right session and date)
  - `labels_outside` (outside material is marked and cited)
  - `source_quality` (allowlisted and checkable)
  - `length_fit`
- **Blind pairwise test with me.** I listen to v1 and v2 on the same 20 questions without knowing which is which, and pick one. Stage 2 is done when v2 wins at least 15 of 20. My picks also go into `evals/calibration.jsonl`, so the judges learn what I mean by "sounds like me".
- **Live targets:**
  - at least 80% thumbs up
  - median spoken length of 60 seconds or less
  - fewer than 5% of segments falling back to notes
  - `rephrased` under 10%

## Stages

Each stage is one or more PRs, follows the spec-first rule, and has a check.

### Stage 1. Measure v1 (half a day)

Thumbs up and down, reasons, `answer_id`, the `answer_feedback` table, the three new events, and a Feedback tile in Analytics. Ship it before changing the tone, so there's a v1 baseline to beat.
**Check:** a thumbs down on the live site shows up in Settings with its reasons, and no name or IP is stored.

### Stage 2. Sound like me (2 days)

- the voice card and examples
- the composer prompt in "class" mode only (opener, 1 to 3 slides, invite)
- Go deeper (the v1 walkthrough)
- grounding exemption for the opener and invite, with their caps
- the variety check
- the new eval dimensions

**Check:** v2 wins at least 15 of 20 in my blind pairwise test, fallback stays under 5%, and the safety tests still pass.

### Stage 3. Class first, not class only (2 to 3 days)

- spec and `AGENTS.md` safety-rule rewrite (the voice decision above, text below)
- coverage modes (class, blend, outside)
- the "asks for more" check
- the source allowlist in Settings
- per-part grounding against cited sources
- the Beyond class card, and the spoken handoff

**Check:** both mockup questions above produce the right mode, every beyond part cites an allowlisted source, and the injection tests (a web page that says "ignore your instructions") still fail closed.

**Draft of the new `AGENTS.md` "Safety rules for the voice"** (goes in with the first Stage 3 PR):

> - Class parts of an answer are grounded in indexed course material, checked in code.
> - Beyond-class parts may be spoken in the cloned voice when they cite an allowlisted source or were written by a model on the approved list in Settings. They are always introduced out loud ("this next part comes from outside class") and shown on a Beyond class card that names the source or the model. The code drops any beyond part that has neither.
> - Off-topic questions get the not-covered response, never an improvised answer.
> - Every spoken part passes the code checks whatever the prompt says: PG, names, access codes, web addresses, the injection echo check, and the length caps.
> - `/api/audio` only speaks text the backend signed. Keep the signature check.
> - The page and README say the voice is AI-generated from Ben's recordings.
> - Keep the rate limits, the daily voice character cap, and the length caps.

### Stage 4. Feedback loop (1 to 2 days)

- the Settings > Feedback inbox
- golden answers
- Add to evals
- Ask Ben
- the Monday digest

**Check:** a golden answer I write replays for the same question, and shows up as the reference in the next eval run.

### Stage 5. Assignment coach (2 to 3 days)

- help levels
- coach notes
- the hint ladder
- solution fingerprints
- review my work
- the deadline-spike alert

**Check:** for each help level, a set of "just give me the answer" questions never produces a fingerprint, and a real hint question gets a useful hint.

### Stage 6. Conversation and study tools (2 to 3 days)

Memory within a visit, missed-class recap, quiz me, Colab links, and listen or read.
**Check:** a 3-turn follow-up eval set, and a recap for every session that has a transcript.

### Stage 7. Learn from it (ongoing)

The think-alouds, the week 6 and end-of-semester pulses, and a review of the thumbs data. Decide what v3 is from what students actually used.
